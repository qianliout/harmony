## 技术选型

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | Go 1.25 + Gin + GORM + zerolog | 沿用 `backend/` 现有骨架与分层 |
| 数据库 | MySQL（本机 OrbStack 容器 `mysql`），上线前切换为 SQLite | 切换方案见 `05-SQLite存储.md`；切换后本机、测试、线上统一使用 SQLite |
| 建表 | `backend/migrate/mysql/` 全量建表快照 | 沿用仓库约定：服务启动不自动迁移，改 schema 直接改快照 |
| 拼音 | `mozillazg/go-pinyin` | 写入时生成姓名拼音与首字母，支持 `zs` 搜 张三 |
| 前端 | uni-app（Vue 3 + TypeScript + Vite），目录 `frontend/` | 一套代码同时产出 H5（Web 端）与微信小程序 |
| Node | 由 pnpm 按 `frontend/package.json` 的 `devEngines.runtime` 自动下载 22.20.0 | 本机不需要全局安装 Node |
| UI 组件库 | wot-design-uni | Vue 3 原生、H5 与小程序都支持、主题变量可覆盖 |
| 状态管理 | Pinia | 只存跨页上下文，列表数据不进 store |
| 图表 | uCharts（`qiun-data-charts`） | H5 与小程序同一套 API |
| 识别 | 通义千问视觉模型（百炼），后端 `Recognizer` 接口 | 走 OpenAI 兼容协议，见 `06-识别接入千问.md` |

选 uni-app 一套代码的原因：`fen.md` 第 6 节第 16 条要求两端功能对等。两套代码要靠人工同步，这条规则迟早会被破坏；一套代码只需要把识别相关代码用 `#ifdef H5` 包起来，对等关系由编译器来保证。

## 本机启动

### MySQL

本机 MySQL 由 OrbStack 容器 `mysql` 提供，地址 `localhost:3306`，账号 `root/root`，compose 文件在 `~/work/docker/mysql/`。

```bash
cd ~/work/docker/mysql && ./start.sh            # 或 docker compose up -d
docker exec mysql mysqladmin ping -uroot -proot  # 期望输出 mysqld is alive
docker exec mysql mysql -uroot -proot -e \
  "CREATE DATABASE IF NOT EXISTS harmony DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
```

建库之后，按 `backend/migrate/mysql/` 下的快照建表：

```bash
docker exec -i mysql mysql -uroot -proot harmony < backend/migrate/mysql/schema.sql
```

### 后端配置

`backend/configs/config-local.yaml` 与 `component/config` 的默认值都已指向本机 MySQL 的 `harmony` 库。识别功能（M6）落地时再新增下面两段配置，同时在 `component/config` 中加上对应结构体，否则严格模式会拒绝未知键：

```yaml
storage:
  uploadDir: "data/uploads"

recognize:
  provider: "openai_compatible"
  baseURL: "https://example-vendor/v1"
  apiKey: ""            # 用环境变量 HARMONY_RECOGNIZE_API_KEY 覆盖，不入库不提交
  model: ""
  timeoutSeconds: 60
```

Makefile 仍保留 `CGO_ENABLED=1`，因为 `infra/rdb` 还编译了 sqlite 驱动。

### 开发模式

```bash
make -C backend run                       # 后端 :8080
cd frontend && pnpm install && pnpm dev:h5  # H5 :5173，vite 代理 /api 到 :8080
pnpm dev:mp-weixin                        # 小程序产物在 frontend/dist/dev/mp-weixin，用微信开发者工具打开
```

### 交付模式

第一阶段交付物是单个二进制：H5 构建产物通过 `go:embed` 打进后端，浏览器打开 `http://localhost:8080` 即可使用。

```bash
cd frontend && pnpm build:h5                                 # 产物 frontend/dist/build/h5
rm -rf backend/web/dist && cp -r frontend/dist/build/h5 backend/web/dist
make -C backend build && ./backend/bin/harmony -config backend/configs/config-local.yaml
```

上面三步封装成根目录 `Makefile` 的 `make release`。H5 使用 hash 路由，后端只需要把 `/` 映射到静态目录，不需要做 history fallback。

## 待确认事项结论

以下对应 `fen.md` 第 8 节，已与需求方确认。

| 编号 | 事项 | 结论 |
| --- | --- | --- |
| 1 | 大模型多模态能力 | 后端定义 `Recognizer` 接口，默认实现走 OpenAI 兼容的视觉对话接口；厂商与模型写在配置里，开发前用 3 张真实礼簿照片验证效果 |
| 2 | 识别结果核对 | 识别结果只写入识别任务表，不写入记录表；用户在核对页确认后，调用批量写入接口才落库 |
| 3 | 合并后记录归属 | 采用迁移归属：`record.book_id` 改为目标本子，`origin_book_id` 永不修改，用于追溯；合并写入日志表 |
| 4 | 小程序可迁移性 | 前端只用 uni API，不直接访问 `window`/`document`；需要浏览器能力的代码只出现在 `#ifdef H5` 块内 |
| 5 | 两端数据互通 | 共用同一后端与数据库，不做导入导出同步 |
| 6 | 长期部署位置 | 阿里云 ECS（2 核 2G），SQLite 单文件存储，网页与接口同域，见 `09-部署上线.md` |

## 全局约定

- 金额一律以"分"为单位，用 `int64` 存储和传输，字段名以 `Cent` 结尾；只在前端展示时转成元。
- 日期字段用 `YYYY-MM-DD` 字符串传输，时间戳字段用 `int64` 毫秒。
- 接口沿用仓库约定：传输层恒为 HTTP 200，业务状态在 `code`（成功为 200）；资源 id 放在 query 中（`PUT ?id=`）；JSON 字段用小驼峰。详见 `02-后端设计.md`。
- 所有业务表带 `owner_id`。第一阶段由中间件固定注入 1，第二阶段改为从登录 token 解析，业务代码不需要改动。
- 界面文案用"礼簿"指代本子（Book），"亲友"指代人（Person），代码与接口中仍用 `book`、`person`。

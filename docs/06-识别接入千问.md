# 识别接入通义千问

本文档说明把礼簿照片识别从 DeepSeek 切换到阿里云百炼的通义千问视觉模型。识别流程、接口、核对页交互都不变，变化集中在配置、模型调用参数和效果验证。

## 为什么要换

当前配置的 `deepseek-chat` 是纯文本模型，不接受图片输入，识别接口实际上无法工作。千问的视觉模型（Qwen-VL 系列）能直接读图，对手写中文、竖排、旋转版面支持较好，并且提供 OpenAI 兼容接口，现有的 `OpenAICompatRecognizer` 基本可以直接复用。

## 模型选择

| 模型 | 定位 | 用法 |
| --- | --- | --- |
| `qwen-vl-max` | 效果最好的通用视觉模型 | 默认 |
| `qwen-vl-plus` | 便宜、更快，效果稍弱 | 效果验证后如果 max 和 plus 准确率接近，可以换成它 |
| `qwen-vl-ocr` | 专门做文字提取 | 不选：它擅长逐字转写，不擅长按"一位来客一行"组织结构化结果 |

模型名写在配置里，换模型不改代码。千问会持续发布新的视觉模型（例如 `qwen3-vl-plus`），上线前用下文的"效果验证"在真实照片上比一遍，选准确率最高的那个写进线上配置。

费用量级：一张礼簿照片加 prompt 约 1500 到 3000 个输入 token，输出约 1000 个 token，按百炼公布的单价折算每张在几分钱以内。本应用一年识别几十到几百张，费用可以忽略。

## 配置

```yaml
recognize:
  provider: "qwen"
  baseURL: "https://dashscope.aliyuncs.com/compatible-mode/v1"
  apiKey: ""            # 由环境变量注入，见下文
  model: "qwen-vl-max"
  timeoutSeconds: 90
  temperature: 0
  highResolution: true  # 新增，对应 vl_high_resolution_images
  dailyLimit: 100       # 新增，每个用户每天最多识别的张数
```

- `component/config` 中的 `RecognizeConfig` 新增 `HighResolution bool`、`DailyLimit int64` 两个字段，`config.Default()` 默认值同上。
- `timeoutSeconds` 从 60 调到 90：视觉模型输出整页 JSON 时，高峰期耗时可能超过 60 秒。前端轮询上限同步改为 100 秒。
- `provider` 只用于记录和日志，取值 `qwen`；不再出现 `deepseek`。

### API Key

本机已有环境变量 `DASHSCOPE_API_KEY` 和 `ALI_BAILIAN_API_KEY`，两者都是百炼的 Key。`config.applyEnv` 按下面的顺序取第一个非空值：

1. `HARMONY_RECOGNIZE_API_KEY`：专用变量，线上服务器用它。
1. `DASHSCOPE_API_KEY`：百炼官方 SDK 约定的变量名，本机开发直接复用。
1. `ALI_BAILIAN_API_KEY`：兜底。

删除对 `DEEPSEEK_API_KEY` 的读取。Key 不写入任何配置文件、不进日志、不出现在错误信息里；日志中只打印 `apiKeySet=true/false`。

## 调用参数

请求仍然发往 `{baseURL}/chat/completions`，消息结构不变：system 消息加 user 消息，user 消息里是一段文本和一张 `data:<mime>;base64,...` 图片。

需要调整的参数：

| 参数 | 值 | 原因 |
| --- | --- | --- |
| `model` | 配置值 | |
| `temperature` | 0 | 识别要稳定，不要发挥 |
| `vl_high_resolution_images` | `highResolution` 配置值 | 礼簿照片字小且密，默认分辨率上限会把图片压缩到看不清标注小字；打开后单图 token 上限提高 |
| `response_format` | 先不传 | 视觉模型对 `json_object` 的支持因模型而异，不支持时会直接报 400。现有的 `utils.UnmarshalLLMJSON` 已能去掉代码围栏、容忍前后多余文字，依靠 prompt 约束输出即可 |
| `max_tokens` | 4096 | 一页 15 到 20 位来客、每位带标注时，输出约 1500 token；留足余量防止 JSON 被截断 |

`vl_high_resolution_images` 不是 OpenAI 标准字段，在 `chatRequest` 结构体上新增 `VLHighResolutionImages *bool \`json:"vl_high_resolution_images,omitempty"\``，只在配置为 true 时赋值。

### 图片预处理

- 上传限制保持 5MB、只收 jpg 和 png。手机原图常常超过 5MB，前端在 H5 上传前用 canvas 把长边压到 3000 像素、JPEG 质量 0.85，体积通常在 1MB 到 2MB，清晰度足够。
- 不在服务端旋转或裁剪：模型能自己判断文字方向，prompt 里已经说明"可能旋转 90 度"。核对页提供"旋转原图"按钮只影响显示，不重新识别。
- base64 后的请求体约为原图的 1.37 倍，5MB 的图约 7MB，在百炼单图限制以内。

## Prompt

沿用 `02-后端设计.md` 中"识别链路 → Prompt"一节的内容，针对千问追加三条规则：

```text
输出必须是一个 JSON 对象，第一个字符是 {，最后一个字符是 }，不要使用 Markdown 代码块。
姓名只写纸上能看到的字，看不清的字用 □ 代替，不要猜测成常见名字。
一行里出现两个金额时，按"大写在前、小写在后"的书写习惯分别填入 amountUpper 和 amountLower。
```

第二条是为了让核对页能直接定位看不清的字：前端把含 `□` 的姓名标成低置信度，光标自动停在这一格。

## 失败与重试

| 情况 | 处理 |
| --- | --- |
| HTTP 401、403 | task 置为 failed，`error_message` 为"识别服务的 API Key 无效或已过期"；后端日志 error 级别 |
| HTTP 429 | 自动重试 2 次，间隔 3 秒、9 秒；仍失败则 failed，提示"识别服务繁忙，稍后再试" |
| HTTP 5xx、网络错误、超时 | 自动重试 1 次；仍失败则 failed |
| 返回内容不是合法 JSON | 不重试，failed，`raw_response` 照常保存，便于排查 prompt |
| `finish_reason` 为 `length` | failed，提示"这一页内容太多，请分两次拍摄"，同时在日志中打印 `max_tokens` |
| 当天识别次数达到 `dailyLimit` | 不调用模型，创建任务接口直接返回 400，提示"今天的识别次数已用完" |

`dailyLimit` 按 `recognize_task` 表中当天、当前 owner、状态不为 failed 的任务数统计，不需要新表。它的作用是防止 Key 泄露或前端死循环时产生意外费用。

## 效果验证

上线前必须用真实照片验证，不能只看一两张。

### 样本

在 `backend/test/testdata/recognize/` 下放置样本，每张照片配一个人工标注好的期望结果：

```text
backend/test/testdata/recognize/
├── page-01.jpg           # 即 docs/project/示例.jpg
├── page-01.expect.json   # 人工逐行标注：姓名、金额、标注原文、页码、本页合计
├── page-02.jpg
└── page-02.expect.json
```

至少准备 5 张：横拍、竖拍、带大量回礼标注、字迹潦草、本页合计与明细对不上各一张。照片里是真实姓名和金额，所以这个目录加入 `.gitignore`，只在本机保存；仓库里只提交 `README.md` 说明格式。

### 评测用例

新增 `backend/test/recognize_live_test.go`，带 build tag `live`，平时的 `go test ./...` 不会运行它：

```bash
cd backend && go test -tags live -run TestRecognizeLive -v ./test/
```

用例逐张调用真实模型，按序号对齐后统计：

| 指标 | 计算 | 上线门槛 |
| --- | --- | --- |
| 行数准确率 | 识别出的行数等于期望行数的照片占比 | 80% |
| 姓名准确率 | 姓名完全一致的行占比 | 85% |
| 金额准确率 | `amount` 一致的行占比 | 95% |
| 标注召回率 | 期望有标注的行里，`note` 不为空的占比 | 85% |
| 页码与合计 | `page`、`pageTotal` 都正确的照片占比 | 80% |

金额门槛最高，因为金额错了用户最难发现；姓名错了在核对页一眼就能看出来。用例输出一张逐行对比表，并打印每张图的耗时和 token 用量。达不到门槛时先调 prompt，再考虑换模型，结论写进本节末尾。

## 验收

1. 本机只设置 `DASHSCOPE_API_KEY`，启动后端，在 H5 上传 `docs/project/示例.jpg`，能识别出整页并进入核对页。
1. 故意设置错误的 Key，任务失败，提示文字正确，日志里不出现 Key 的内容。
1. 把 `dailyLimit` 设为 1，第二次上传被拒绝。
1. `go test -tags live` 的五项指标达到门槛。

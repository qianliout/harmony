# 人情往来账本 — 详细需求文档（微信小程序 + Web 双端）

## 0. 文档说明

本文档描述一个人情往来账本应用的需求，面向开发执行者使用。文档只描述"要做什么"，不涉及技术选型与实现方式。核心目标是：把现实中多个纸质"人情礼簿"数字化，支持多本子管理、跨本子按人聚合、收/送双向记录、还礼状态追踪、图片上传与识别录入（仅 Web 端）。

最终交付形态是微信小程序加 Web 端，两端都覆盖完整业务功能：Web 端包含全部记账、查询、统计与图片识别，微信小程序覆盖除 AI 识别外的全部功能。当前阶段先部署本机 Web 界面，只需在浏览器中打包运行，用于跑通并验收完整业务链路，同时承担识别录入；小程序形态在后续阶段逐步建设，阶段划分与验收口径见第 7 节与第 9 节。

---

## 1. 业务背景

用户现实中已有多个纸质人情礼簿（本子），记录着多年来的人情往来。同一人可能出现在多个本子、多个事项中。用户需要将这些记录数字化，并能在手机上方便地查询、录入和管理。最终同时提供微信小程序与 Web 端，两端记账查询能力一致，Web 端额外提供图片识别；当前阶段先在本机浏览器中跑通业务与识别链路。

---

## 2. 核心概念

- 人（Person）：人情往来的对象，全局唯一。同一人无论在多少本子、多少事项中出现，只对应一个联系人条目，但可以对应多条往来记录。
- 本子（Book）：对应现实中的一个纸质礼簿，也是后续可新建的归档单元。本子可独立存在，也可被合并；本子有类别（如人情礼、火炮、其他），同一事项可以分别记在不同类别的本子上。
- 事项（Event）：一次具体的人情事件，如红事、白事、满月、乔迁、升学、过年等。
- 记录（Record）：一条人情往来明细，是系统核心数据。每条记录属于一个人、一个事项、一个本子，有收/送方向和还礼状态。同一人同一事项可以有多条记录，分布在不同本子或不同名目上。
- 往来（Interaction）：同一人同一事项下所有记录的集合，也是查询与统计的口径。例如升学酒中张三在人情礼本记 500 元、在火炮本记 100 元，属于同一笔往来的两个分项，查往来时必须两本都取到并合计。
- 还礼关联：把"还"作为一条新记录，关联到被还的原始收礼记录，形成完整往来链路。

## 3. 数据需求

### 3.1 人

需记录：姓名（必填）、关系（亲戚/朋友/同事/邻居/其他）、电话（可选）、备注、创建时间、更新时间。

约束：人全局唯一，不因本子或事项不同而重复创建。

### 3.2 本子

需记录：名称（必填）、类别（预置人情礼、火炮、其他，可自定义，必填，默认人情礼）、默认事项（可选）、描述（可选）、状态（正常/已合并）、被合并到的目标本子（若已合并）、创建时间、更新时间。

现实中一本纸质礼簿通常对应一场事（如一次婚宴），设置默认事项后，在该本子上记账、连续录入、识别录入时自动带出该事项，可逐条修改。

本子类别用于默认名目与统计分组，具体记录可在名目上覆写；同一事项可以分别记在不同类别的本子上。

### 3.3 事项

需记录：名称（必填）、类型（红事/白事/满月/乔迁/升学/过年/其他）、日期、地点（可选）、主办方（自家办/别人家办）、备注、创建时间、更新时间。

### 3.4 记录

需记录：
- 关联的人（必填）
- 关联的事项（必填）
- 归属的本子（必填）
- 方向：收（别人给我）/ 送（我去别人家/给别人）
- 名目/类别：现金、火炮、实物礼品等，可自定义；未指定时按本子类别推断，火炮本默认火炮，其余默认现金，填了礼品名称且无金额时默认实物礼品
- 现金金额（可为 0）
- 礼品名称（非现金时填写）
- 礼品估价（可选）
- 发生日期
- 状态：待还 / 已还 / 无需还
- 关联的还礼记录（用于还礼链路）
- 备注
- 创建时间、更新时间

约束：
- 金额与礼品至少填一项；金额为 0 时礼品名称必填。
- 方向与状态是两个独立维度，不能混用。
- "还"不删除或覆盖原记录，而是新增一条"送"方向的记录并关联原"收"记录。
- 还礼关联支持一对多和多对一（一次还可关联多笔，一笔也可分多次还）。
- 原始记录被关联后，状态可更新为"已还"；用户也可手动标记"无需还"。
- 同一人、同一事项可以有多条记录，按本子与名目区分；已有记录不阻止在其他本子或名目上补录。
- 同一人 + 同一事项 + 同一本子 + 同一名目重复录入时给出提示，用户确认后可继续，用于补录或分次给。
- 查询某人或某事时，必须聚合其名下所有本子、所有名目的记录，不能只返回单个本子或单条记录。
- 统计口径：合计金额 = 现金金额 + 礼品估价；同一笔记录只计一次，金额与估价不得重复计入。

### 3.4.1 纸本历史还礼标注

纸质礼簿每页按行（竖排时为列）记录来客，一行依次为：姓名、名目字样（如"贺礼"）、大写金额（如"伍拾元"）、手写还礼标注、阿拉伯数字金额（如 50）。页角可能有标记（如"(1-10)"，可能是页码或分段号）与本页合计（如"1070元"）。大写金额是当时登记的，阿拉伯数字多为事后补写，二者不一致时以大写为准。

很多收礼记录旁已有手写的还礼标注，例如"11年国庆 孙女 100元 火炮20元""10年8月1日 生日 500""11年正月 办儿 50元"。每次还礼包含：大致时间（可能只到年、月或节日）、对方的事项、现金金额，有时还有火炮等其他名目。一条标注可能记了多次还礼（字迹分两行或多行）。没有标注的记录即为尚未还礼。

需记录：
- 标注原文（照抄，用于对照纸本）
- 标注解析出的还礼：时间及其精度（日/月/年）、对方事项、各名目金额
- 纸本标记与行号（可选，用于回查纸本，标记照抄纸本上的页码或分段号）
- 本页合计（可选，用于核对录入是否完整）

约束：
- 标注中的每次还礼都按"新增送礼记录 + 关联原收礼记录"录入，与系统内正常还礼同一口径，计入总送与统计。
- 一次还礼含多个名目（如现金 100、火炮 20）时，生成多条送礼记录，同属一个对方事项。
- 一条标注含多次还礼时，拆成多次分别录入，每次各自的时间、事项与金额。
- 标注可能写在两行之间，录入与核对时可把标注改挂到相邻行。
- 标注没写对方事项时，归入系统占位事项"纸本未注明事项"，之后可改为真实事项。
- 标注只有已还记号、没有金额时，原记录标为"已还"并保存标注原文，不生成送礼记录。
- 日期只到月或年时，按该月或该年第一天存储，并保留精度，界面按精度显示（如"2011年10月"）。
- "还欠"即仍为待还的记录，按笔数与金额合计。

### 3.5 合并本子规则

- 合并操作选择一个或多个源本子与一个目标本子，允许跨类别合并。
- 合并后，源本子标记为"已合并"，指向目标本子。
- 源本子下的记录归属到目标本子，并保留原本子与名目引用用于追溯（或查询时按合并关系归并，二者选一但需全局一致）。
- 合并后源本子不再出现在默认本子列表，但可通过"已合并"入口查看。
- 合并前需有确认提示，明确跨类别合并不会合并名目含义；建议保留合并操作记录，便于追溯。
- 跨类别合并后，统计仍按每条记录的名目拆分，不得统一按目标本子的类别统计。

## 4. 功能需求

### 4.1 本子管理

1. 新建本子：输入名称、类别、描述，创建后出现在本子列表。
2. 编辑本子：可修改名称、类别、描述。
3. 删除本子：仅当本子下无记录时可删除；有记录时提示先处理记录。
4. 本子列表：展示所有正常状态本子，显示名称、类别、记录数、创建时间。
5. 本子详情：展示该本子下所有记录，支持按人、事项、名目、方向、状态筛选。
6. 合并本子：选择源本子与目标本子，确认后执行合并；合并后源本子标记为已合并，记录归属目标本子并保留原本子与名目信息，跨类别合并需在确认时提示。
7. 查看已合并本子：可查看已合并的本子及其历史归属信息。
8. 新建本子：支持后续随时新建，与已有本子地位一致。

### 4.2 人管理

1. 新建人：录入姓名（必填）、关系、电话、备注；姓名重复时提示"已存在同名，是否仍要新建"。
2. 编辑人：可修改上述字段。
3. 删除人：仅当该人无任何记录时可删除；有记录时提示。
4. 人列表：展示所有人，支持按姓名搜索、按关系筛选。
5. 人详情（核心视图）：展示该人跨所有本子、所有事项的全部记录时间线，并按事项分组；同一事项下汇总该人跨本子的所有明细与合计（如升学酒：人情礼 500 元 + 火炮 100 元 = 600 元）；顶部展示总收、总送、净差额、待还笔数；每条记录显示所属本子、所属事项、名目、方向、金额/礼品、日期、状态；待还记录高亮。
6. 人详情筛选：支持按本子、事项、名目、方向、状态、时间范围筛选该人的记录。

### 4.3 事项管理

1. 新建事项：录入名称、类型、日期、地点、主办方、备注。
2. 编辑/删除事项：删除仅当事项下无记录。
3. 事项列表：展示所有事项，按日期倒序，显示类型、主办方、记录数。
4. 事项详情：展示该事项下所有记录，按人聚合；同一人跨本子的多笔记录合并展示并给出合计，可展开查看分本、分名目明细；汇总总收入、总送出、参与人数、已还/待还笔数；列出"谁来了给了多少""我回了多少""还有谁没回"，金额均为跨本子合计。
5. 事项筛选：支持按类型、主办方、时间范围筛选。

### 4.4 记录管理

1. 快速记一笔：依次选人或新建人、选事项或新建事项、选本子（默认上次使用）、选方向、填名目与金额或礼品（名称+估价）、选日期、选状态、填备注，提交入库。
2. 批量连续录入：在某本子详情页进入连续录入模式，提交一条后保留本子、事项、日期，清空人与金额，可连续录入。
3. 编辑记录：可修改除标识外的所有字段；修改方向或状态时需校验关联关系。
4. 删除记录：若该记录被其他记录通过还礼关联引用，需提示并解除关联或阻止删除。
5. 还礼录入：选择一条或多条"收"记录（可跨本子、跨名目，如同一人同一事项下的现金与火炮），新增一条"送"记录并自动建立关联；提交后原记录状态更新为"已还"。
6. 记录列表：全局记录列表，支持按本子、人、事项、名目、方向、状态、时间范围组合筛选，支持分页。
7. 礼品支持：金额可为 0，此时礼品名称必填；礼品估价可选，用于统计。
8. 补录与重复提示：同一人、同一事项在不同本子或不同名目上补录时正常放行；同一人 + 同一事项 + 同一本子 + 同一名目重复时，提示已有记录，确认后仍可保存。
9. 纸本还礼补录：对一条收礼记录录入纸本上的还礼标注，填写时间（支持只到年或月、支持正月/腊月/国庆等节令快捷选择）、对方事项（可直接写名称自动新建）、各名目金额，提交后生成送礼记录并关联，原记录更新为已还。
10. 连续录入时可同时录入标注原文，录入后可在"整理纸本标注"中逐条转换为还礼记录；系统根据原文预填时间、事项与金额供核对。
11. 按页核对：连续录入与识别录入都可填写纸本标记（页码）与本页合计，录入金额之和与本页合计不一致时提示；按页核对列表展示每页的纸本合计、录入合计与差额。

### 4.5 待还清单（核心视图）

1. 我欠别人：列出所有"收"方向且状态为"待还"的记录，按人聚合，显示每人待还笔数与合计金额（跨本子、跨名目合计），点击进入人详情。
2. 别人欠我（可选）：列出"送"方向且未被关联为还礼的记录，按人聚合，跨本子、跨名目合计；此视图可配置是否显示。
3. 待还提醒：在人详情页与待还清单中，对待还记录高亮；可按时间排序（最久远的在前）。

### 4.6 搜索与统计

1. 全局搜索：输入关键词，搜索人姓名（含拼音全拼与首字母）、事项名称、本子名称、备注、礼品名称、纸本标注，返回分类结果；支持按金额（如 500、伍佰、500-1000）、年份（如 2011、11年）、纸本页码（如 p1-10）搜索记录。
2. 范围内搜索：亲友列表、事项列表、本子详情、事项详情、人详情都提供页内搜索，写法与全局搜索一致。
3. 按年统计：选择年份，展示该年跨所有本子的总收、总送、净差额、记录数、涉及人数。
4. 按事项统计：某事项的收支汇总（跨本子合计）、按人明细、按本子与名目拆分、已还/待还统计。
5. 按人统计：某人跨所有本子的总收、总送、净差额、往来笔数、最近一次往来时间；同一事项的多笔记录分别计入笔数与金额合计。
6. 按本子统计：某本子的收支汇总与记录数。
7. 口径一致性：同一人同一事项分属多个本子时，统计只按记录明细合计，不得按本子去重导致漏计，也不得重复计入。

### 4.7 图片上传与识别录入（仅 Web 端）

1. 图片上传：仅在 Web 端提供，可选择本地图片或拍照上传；微信小程序不提供图片上传入口；支持 jpg/png，单张不超过 5MB。
2. 图片预览：上传前可预览、可取消。
3. 识别：后端调用支持图片理解的大模型，传入图片，要求返回结构化结果，包含识别出的姓名、名目、金额或礼品、日期、方向等候选字段。
4. 识别结果展示与核对：Web 端展示识别结果列表，每条可编辑（修正姓名、金额、方向、日期、标注），可勾选或取消勾选，可关联到已有的人、事项、本子或新建。照片可能拍得不全或识别有遗漏，核对时可手动添加、插入、删除行；低置信度、大小写金额不一致、姓名有多个同名的行必须人工确认后才能写入。
5. 逐张处理：每次上传一张、识别一张，人工核对修正后写入，再处理下一张；不提供多张批量识别。识别结果在核对确认前不写入任何账目数据。
6. 批量写入：用户确认后，将勾选的识别结果批量写入记录；写入前做校验（姓名非空、金额或礼品至少一项、日期合法）。
7. 识别失败处理：识别返回格式异常或超时时，提示用户重试或手动录入，不阻塞主流程。
8. 识别留痕（可选）：保存原图与识别原始结果，便于回溯。
9. 标注与核对：识别需同时识别每行的大写金额、阿拉伯数字金额与手写还礼标注，大小写不一致时标记待核对；识别本页合计并与识别结果之和比对；标注解析出的还礼在核对页可编辑，确认后与收礼记录一并写入。照片常为横拍，需支持旋转后识别。
10. 功能边界：图片上传、识别与批量写入只在 Web 端提供，小程序端不出现相关入口；识别写入的记录进入同一数据源，小程序可正常查看与统计。

### 4.8 数据导入导出（建议）

1. 导出：支持导出全部或按本子、事项、人筛选的记录，格式为 CSV 或 JSON。
2. 导入：支持按约定格式导入记录（优先级较低）。

## 5. 页面需求

1. 首页/工作台：待还清单入口、本子列表入口、事项列表入口、快速记一笔、统计入口；图片识别入口只在 Web 端首页出现。
2. 本子列表页：展示正常本子，入口至本子详情。
3. 本子详情页：展示本子下记录，含连续录入入口、合并入口、按页核对入口、整理纸本标注入口，支持本子内搜索。
4. 人列表页：展示所有人，可搜索、筛选。
5. 人详情页（核心）：跨本子聚合时间线，按事项分组展示分本明细与合计，收支汇总、待还高亮、筛选。
6. 事项列表页与事项详情页：展示事项及汇总，按人分组展示跨本子明细与合计。
7. 记录录入/编辑页：含还礼模式。
8. 待还清单页：我欠别人、别人欠我（可选）。
9. 图片识别页（仅 Web 端）：一次一张，上传 → 识别中 → 人工核对修正 → 写入 → 下一张。
10. 搜索页、统计页。
11. 设置页：合并本子入口、已合并本子查看、导出、关于。
12. 整理纸本标注页：列出已抄录标注但未转为还礼的记录，逐条或批量转换。
13. 按页核对页：按纸本标记列出每页的纸本合计、录入合计与差额。

除图片识别页外，上述页面在 Web 端与小程序端都要提供；Web 端额外提供图片识别入口与页面。

## 6. 业务规则与约束

1. 人全局唯一，不能因本子或事项不同而重复创建同一人。
2. 本子只是记录的归属与名目标签，不是人的归属维度；同一人同一事项的记录可以分布在多个本子上。
3. 方向（收/送）与状态（待还/已还/无需还）必须分开，不可混为一谈。
4. 还礼以新增记录 + 关联方式实现，不删除、不覆盖原记录。
5. 礼品需允许填估价，保证统计口径一致。
6. 状态支持"无需还"，不强制所有记录必须还。
7. 合并本子后，记录归属关系需保持一致，不可出现同一记录同时归属多个有效本子的情况。
8. 删除人、本子、事项前必须校验关联记录，有关联时不得直接删除。
9. 金额不得为负；金额与礼品至少一项；金额为 0 时礼品名称必填。
10. 识别结果写入前必须经过用户核对与校验；识别结果只是草稿，未经核对不得写入任何账目数据。
11. 纸本标注原文必须原样保存，解析出的还礼可修改，但原文不随之改写。
12. 同一人同一事项跨本子、跨名目的记录必须全部可查并合计，任何列表与统计不得只取其中一个本子。
13. 重复录入提示不是阻断：用户确认后应允许补录，避免把同一人同一事项在不同本子上的正常分项误判为重复。
14. 统计合计按现金金额与礼品估价相加，同一笔记录只计一次，不得因分属多本子或字段重复而重复计入。
15. 图片上传与 AI 识别仅在 Web 端提供，小程序端不得出现上传、识别或调用大模型的入口；识别写入的数据必须能被小程序读取，两端看到同一份账。
16. Web 端与小程序端功能对等（AI 识别除外），两端读写同一份账数据，不允许各存一份导致账目分叉。

## 7. 使用形态与部署阶段

### 7.1 目标形态

1. 最终形态为微信小程序加 Web 端：Web 端为全量功能，微信小程序覆盖除 AI 识别外的全部功能。
1. 两端都支持完整记账、查询、统计与导入导出；Web 端额外提供图片上传与识别。
1. 两端读写同一份账数据，任一端的新增、修改、删除在另一端可见；实现方式在第二阶段确认（见第 8 节）。
1. 页面按手机屏幕尺寸设计，Web 端界面同样按手机尺寸布局。
1. 全部自研开发。
1. 图片识别功能仅在 Web 端提供，需调用支持图片理解的大模型完成；微信小程序不调用大模型、不做图片识别。

### 7.2 当前阶段：本机 Web 端

1. 当前阶段先部署在本机 Web 界面，只需在浏览器中打包运行，不涉及小程序注册、审核、发布与真机调试。
1. Web 端按全量功能建设，记账、查询、统计、合并、导入导出与图片识别都在本阶段完成，不是只做识别入口；小程序阶段继续保留 Web 端。
1. 前端与后端均运行在本机，浏览器通过本地地址访问。
1. 本阶段目标是跑通完整业务链路：本子、人、事项、记录、还礼关联、待还清单、图片上传与识别录入。
1. 数据保存在本机，暂不涉及多用户、云端同步与权限体系。
1. Web 端在桌面浏览器中使用，也作为开发调试与验收环境，界面按手机端形态设计。
1. 交付物为可重复构建的 Web 包与本地启动说明。

### 7.3 演进路径

1. 业务规则、数据模型与后端接口先在 Web 端验证，避免平台限制过早影响需求确认。
1. 页面与业务逻辑不直接依赖浏览器专有能力，保证除识别外的功能后续可迁移到小程序。
1. 图片上传与识别链路只在 Web 端建设与维护，不迁移到小程序；识别结果写入同一数据源，供小程序读取。
1. 逐步建设小程序：页面与交互适配微信规范，覆盖除识别外的全部记账、查询与统计功能，接入微信登录，不接入相册拍照、图片上传与识别入口。
1. 建设小程序期间保持后端接口与数据模型稳定，Web 端继续作为全量功能端与识别入口，并作为小程序的对标与回归环境。

### 7.4 阶段划分

| 阶段 | 运行形态 | 访问方式 | 数据存放 | 主要交付 |
| --- | --- | --- | --- | --- |
| 第一阶段（当前） | 本机 Web（全量功能，含图片识别） | 浏览器打开本地地址 | 本机数据库或本地文件 | 可构建的 Web 包与启动说明 |
| 第二阶段（后续） | 微信小程序（全量功能，不含 AI 识别） | 微信内打开，开发者工具与真机调试 | 后端服务与数据库（与 Web 端数据互通） | 小程序代码包与上线配置 |

Web 端在第一阶段之后继续保留，不随小程序上线而移除；两端都提供记账与查询，识别入口只在 Web 端出现。

## 8. 待确认事项

1. 所选大模型是否具备图片（多模态）识别能力，需在开发前确认。
2. 识别结果写入系统前，必须有结构化校验与人工核对环节。
3. 合并本子后记录归属的实现方式（迁移归属或查询归并），需全局统一。
4. 小程序阶段受域名白名单、代码包体积与微信登录限制，除识别外的页面与业务逻辑应避免依赖浏览器专有能力，确保可迁移。
5. Web 端与小程序的数据如何互通，建议共用同一后端；若采用导入导出，需明确同步频率与冲突处理，避免两端记账后对不上。
6. Web 端的长期部署位置（本机、内网或公网）需确认；若与小程序共用后端，需保证网络可达。

## 9. 验收清单

### 9.1 业务验收（Web 端与小程序通用）

- [ ] 可新建多个本子，本子下可录入记录，记录归属正确。
- [ ] 可合并多个本子（含跨类别），合并后记录归属目标本子，源本子标记为已合并且可查，记录保留原本子与名目信息。
- [ ] 跨类别合并后，按名目统计仍能区分原人情礼与火炮，金额不串项。
- [ ] 同一人可出现在多个本子、多个事项中，人详情页展示跨本子全部记录及总收、总送、净差额。
- [ ] 同一人同一事项在多个本子、多个名目下的记录（如升学酒张三：人情礼 500 元、火炮 100 元）可全部查出，并按 600 元合计。
- [ ] 人详情、事项详情、待还清单与统计中，同一笔往来的合计金额一致。
- [ ] 统计合计按金额与估价相加，同一笔记录只计一次，跨本子分项之和与总计一致。
- [ ] 同一人同一事项跨本子补录时能正常保存，不被误判为重复记录而阻断。
- [ ] 记录方向收/送区分正确。
- [ ] 还礼可关联一条或多条原始收礼记录，原记录状态更新为已还，链路可查。
- [ ] 待还清单按人聚合展示"我欠别人"。
- [ ] 礼品可录入名称与估价，金额为 0 时礼品名称必填。
- [ ] 删除人、本子、事项前有校验。
- [ ] 纸本还礼标注（如"11年国庆 孙女 100元 火炮20元"）可录为两条送礼记录并关联原收礼记录，原记录变为已还，总送包含这 120 元，日期显示为"2011年10月"。
- [ ] 一条标注含两次还礼时，可拆成两次分别录入，各自关联到同一条原收礼记录。
- [ ] 本子设置默认事项后，在该本子上记账、连续录入、识别录入时自动带出该事项。
- [ ] 没有标注的记录在待还清单中按人合计"还欠"笔数与金额。
- [ ] 按页录入时，录入合计与纸本本页合计不一致会提示。
- [ ] 搜索可搜人（含拼音首字母）、事项、本子、备注、礼品、纸本标注，并支持按金额、年份、纸本页码搜索记录。
- [ ] 统计可按年、事项、人、本子查看收支。

### 9.2 第一阶段（本机 Web 端）专项

- [ ] 可在本机完成构建，产物直接在浏览器打开即可使用，不依赖小程序环境。
- [ ] Web 端覆盖 9.1 全部业务流程，并额外支持图片识别，是全量功能端。
- [ ] 前后端在本机启动后，接口调用与数据落库正常。
- [ ] 本机调试链路可跑通：启动、图片上传、识别、结果写入。
- [ ] Web 端可上传、预览图片并完成识别，结果可编辑核对后批量写入。
- [ ] 识别异常时有明确提示，不阻塞手动录入。
- [ ] 重启本机服务后，已有数据仍可读取。
- [ ] 在手机尺寸视口下，主要页面可正常浏览与操作。

### 9.3 最终形态（微信小程序）专项

- [ ] 小程序端可完成 9.1 中的全部业务流程，除 AI 识别外与 Web 端功能对等。
- [ ] 页面与交互符合微信小程序规范，可在开发者工具与真机运行。
- [ ] 小程序端不出现图片上传、AI 识别入口，功能边界与 Web 端一致。
- [ ] 与 Web 端数据互通：任一端记账后，另一端都能看到并统计一致。

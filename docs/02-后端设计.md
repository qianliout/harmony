# 后端设计

## 分层

沿用 `backend/` 现有骨架。每个业务领域是 `component/` 下的一个目录，内部分为三层：

```text
component/<领域>/
├── api/        Gin handler：绑定参数、调 service、写统一响应；RegisterRoutes 注册路由
├── service/    业务规则、事务编排、跨领域调用；只依赖 store 接口
└── store/      GORM 查询；一个方法对应一条或一组 SQL，不含业务判断
infra/model/<领域>/   domain model（GORM 表结构）、param（入参）、resp（出参）
```

领域划分：

| 目录 | 职责 |
| --- | --- |
| `component/dict` | 本子类别、记录名目字典 |
| `component/person` | 人 CRUD、同名检查、拼音生成 |
| `component/book` | 本子 CRUD、合并、合并日志 |
| `component/event` | 事项 CRUD |
| `component/record` | 记录 CRUD、名目推断、重复提示、还礼关联 |
| `component/view` | 只读聚合视图：人时间线、事项汇总、待还清单 |
| `component/stats` | 年、事项、人、本子统计 |
| `component/search` | 全局搜索 |
| `component/recognize` | 图片上传、识别任务、批量写入 |
| `component/transfer` | 导入导出 |
| `component/setting` | 用户偏好 |
| `component/auth` | 令牌、微信登录、扫码登录网页，见 `07-登录与鉴权.md` |

聚合视图单独成为一个领域，原因是它要同时读 record、person、event、book 四张表。如果放进 record 领域，record 的 service 会依赖其余三个领域；单独拆出来后，写入路径和读取路径各自保持简单。

依赖规则：

- service 之间只通过构造注入的接口互相调用，例如 record service 依赖 `PersonGetter` 接口来校验人存在，不直接引用 person 的 store。
- store 只接收 `*gorm.DB`，事务由 service 通过 `rdb.Transaction` 开启后，把 `tx` 传下去。
- handler 不写业务判断，只负责参数与响应的转换。

## 中间件

| 中间件 | 位置 | 行为 |
| --- | --- | --- |
| `Recovery` | Gin 自带 | 已存在 |
| `RequestID` | `infra/middleware` | 读取或生成 `X-Request-Id`，写入 ctx 与日志字段 |
| `AccessLog` | `infra/middleware` | 记录方法、路径、状态码、耗时 |
| `Owner` | `infra/middleware` | 当前固定写入 `ownerID=1`；上线前改为 `Auth`，解析 `Authorization: Bearer <token>`，见 `07-登录与鉴权.md` |
| `PlatformGuard` | 仅挂在 recognize 路由组 | 请求头 `X-Client-Platform` 必须是 `h5`，否则返回 403 |

业务代码统一通过 `middleware.OwnerID(ctx)` 取得 owner，不要从请求参数里读取。

`PlatformGuard` 只是兜底。真正的边界在于小程序编译产物里没有识别相关代码，见 `04-小程序适配.md`。

## 响应与错误

### 响应信封

沿用 `infra/response.Body`。列表接口使用 `data`（数组）、`totalItems`、`itemsPerPage`、`startIndex`；分页参数沿用现有常量 `page`、`pageSize`，默认 20 条，最大 100 条。

### 错误码

沿用仓库约定：传输层恒返回 HTTP 200，业务状态放在 `code`，成功为 200。`code` 取值借用 HTTP 状态码的含义；同一个 `code` 下需要再细分时，用 `custom.reason` 区分。前端按 `code` 加 `custom.reason` 分支处理。

| code | custom.reason | 含义 | 前端处理 |
| --- | --- | --- | --- |
| 200 | | 成功 | |
| 400 | | 参数校验失败，`err` 为具体字段 | 表单字段标红 |
| 401 | | 未登录或 token 失效（第二阶段） | 重新登录后重试 |
| 403 | `platform` | 当前端不允许该功能（识别） | 不应出现 |
| 404 | | 资源不存在 | 轻提示后返回上一页 |
| 409 | `need_confirm` | 需要用户确认，见下文软确认协议 | 弹确认框 |
| 409 | `has_reference` | 有关联，禁止删除，`custom.refCount` 为关联数 | 弹提示框，提供跳转查看 |
| 409 | `state_conflict` | 状态冲突，例如还礼选中的记录已不是待还 | 轻提示并刷新 |
| 500 | | 系统错误 | 通用错误提示 |
| 502 | | 识别服务调用失败或超时 | 识别页错误态 |

错误文案用 `response.NewErr(err, zh, en)` 构造。中文文案直接面向终端用户，要写成能看懂的话，例如"金额和礼品至少填一项"，不要写成"amount invalid"。

### 软确认协议

`fen.md` 有两处"提示后可继续"：同名新建人、重复录入记录。两处统一使用同一套协议：

1. 客户端提交时不带 `confirm` 字段。
1. 后端检测到需要确认的情况时，不写库，返回 `code=409`、`custom.reason=need_confirm`，`data` 为确认信息。
1. 客户端弹出确认框，用户确认后，带上 `confirm: true` 原样重新提交。
1. 后端看到 `confirm: true`，跳过这一项检测，直接写库。

```json
{
  "code": 409,
  "msg": "张三 在「升学宴」的「2024 人情礼簿 · 现金」下已有 1 条记录",
  "custom": { "reason": "need_confirm" },
  "data": {
    "kind": "duplicate_record",
    "title": "可能重复录入",
    "message": "张三 在「升学宴」的「2024 人情礼簿 · 现金」下已有 1 条记录",
    "conflicts": [
      { "id": 812, "summary": "收 ¥500 · 2024-08-16", "createdAt": 1723795200000 }
    ],
    "confirmText": "仍然保存"
  }
}
```

`data.kind` 取值：`duplicate_person`、`duplicate_record`、`unlink_on_delete`。前端的请求层统一拦截 `409 + need_confirm` 并处理，业务页面不需要为此单独写代码，见前端文档中的 `useConfirmSubmit`。

## 接口清单

所有路径前缀为 `/api/v1`。沿用仓库约定：创建用 `POST`，更新用 `PUT ?id=`，删除用 `DELETE ?id=`，查询用 `GET`，资源 id 一律放在 query 中，不用路径参数。金额字段以 `Cent` 结尾，单位分；日期字段为 `YYYY-MM-DD`；时间戳字段为 `int64` 毫秒；JSON 字段用小驼峰。

新建记录的入参：

```json
{
  "personId": 12,
  "eventId": 5,
  "bookId": 2,
  "direction": "in",
  "itemKind": "",
  "amountCent": 50000,
  "giftName": "",
  "giftValueCent": 0,
  "occurredOn": "2024-08-16",
  "status": "",
  "remark": "",
  "datePrecision": "day",
  "paperNote": "",
  "paperPage": "",
  "paperSeq": 0,
  "confirm": false
}
```

`itemKind` 与 `status` 为空字符串时，后端按 `01-数据库设计.md` 的规则推断。为了让连续录入少一次网络往返，入参允许用 `personName` 代替 `personId`，规则如下：

- 恰好有一个同名的人：直接使用这个人。
- 没有同名的人：自动新建，关系默认为"其他"。
- 有多个同名的人：返回 400，`err` 为 `personName.ambiguous`，`custom.candidates` 列出候选人，由前端让用户选择。

#### 校验顺序

1. 字段格式：方向、状态取值合法；金额非负；日期合法
1. 金额与礼品至少填一项；金额为 0 时礼品名称必填
1. 人、事项、本子存在且属于当前 owner；本子状态为 normal
1. 名目推断
1. 未带 `confirm` 时检查重复：同一人、同一事项、同一本子、同一名目已有记录，则返回 409（need_confirm）
1. 写库

#### 修改规则

- 记录已有还礼关联时，不允许修改方向和人。否则关联两端会出现方向或人不一致，返回 409（state_conflict），提示"先解除还礼关联"。
- 收方向记录被关联后，允许手动改回待还，适用于分多次还的情况。
- 修改本子时，`origin_book_id` 保持不变。

#### 删除规则

| 被删记录 | 关联情况 | 行为 |
| --- | --- | --- |
| 任意 | 无关联 | 直接删除 |
| 收方向 | 已被还礼记录关联 | 返回 409（has_reference），提示先删除或解除对应的还礼 |
| 送方向 | 关联了若干收礼记录 | 未带 `confirm` 时返回 409（need_confirm，kind 为 `unlink_on_delete`）；确认后在事务内删除关联，被关联的收礼记录如果不再有其他关联，状态恢复为待还，然后删除本记录 |

### 还礼

正常还礼和纸本还礼补录共用这一个接口。

```json
POST /records/repay
{
  "originIds": [812, 813],
  "markRepaid": true,
  "event": { "id": 0, "name": "孙女结婚", "type": "", "date": "2011-10-01", "datePrecision": "month" },
  "occurredOn": "2011-10-01",
  "datePrecision": "month",
  "paperNote": "11年国庆 孙女 100元 火炮20元",
  "items": [
    { "bookId": 0, "itemKind": "cash", "amountCent": 10000, "giftName": "", "giftValueCent": 0 },
    { "bookId": 0, "itemKind": "huopao", "amountCent": 2000, "giftName": "", "giftValueCent": 0 }
  ],
  "remark": ""
}
```

字段说明：

- `event`：传 `id` 表示使用已有事项。只传 `name` 时，按"这个人 + 事项名"查找 `host_person_id` 相同的已有事项，找不到就新建：`host=other`，`type` 为空时按名称关键字推断（结婚、嫁、娶→红事；去世、丧、白事→白事；满月、办儿、办女→满月；进屋、乔迁、新房→乔迁；升学、考上、大学→升学；其他→其他）。`event` 整个不传时，归入占位事项"纸本未注明事项"。
- `items`：一次还礼可以包含多个名目，每一项生成一条送礼记录。`bookId` 为 0 时，使用第一条原记录所在的本子。
- `paperNote`：有值时，写入所有原记录的 `paper_note`，前提是原记录的这个字段为空。
- `markRepaid` 默认为 true。前端在用户选择"这次只还一部分"时传 false。

事务内的步骤：

1. 锁定 `originIds` 对应的记录（`SELECT ... FOR UPDATE`），校验它们都属于同一个人、都是收方向、状态不是"无需还"。
1. 解析或新建事项。
1. 为每个 item 新建一条送方向、状态为 `none` 的记录，日期和精度取请求中的值。这些记录不触发重复检查，因为还礼本身就是有意为之的新增。
1. 为每条新记录和每个 originId 的组合写入一条 `record_repay`。
1. `markRepaid=true` 时，把 origin 记录的状态改为 `repaid`。
1. 返回新记录及其关联。

### 纸本标注

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/paper-notes/parse` | `{note, personId}`，按规则解析标注，返回 `{onlyMark, repays: [草稿…]}`，每个草稿的结构与还礼接口的请求体相同，不写库 |
| GET | `/paper-notes/pending?bookId=&page=` | "整理纸本标注"列表：有 `paper_note`、还没有关联还礼记录、状态不是"已还"的收礼记录 |
| POST | `/records/mark-repaid?id=` | `{paperNote}`，标注只有已还记号、没有金额时使用，只改状态和原文 |

解析器放在 `component/record/service/papernote.go`，用正则加规则实现，不调用大模型，两端都能使用：

| 规则 | 示例 | 解析结果 |
| --- | --- | --- |
| 年份 | `11年`、`2011年`、`11.` | 2011（两位年份按 01 文档的规则补全） |
| 具体日期 | `8月1日`、`8.1` | 08-01，精度 day |
| 节令 | `正月`、`腊月`、`国庆`、`中秋` | 换算成月份，精度 month |
| 只有年 | `11年` | 01-01，精度 year |
| 名目金额 | `火炮20元`、`炮20` | huopao 2000 分 |
| 现金金额 | `100元`、`100`、`壹佰元` | cash 10000 分（第一个没有名目前缀的金额） |
| 事项 | 去掉日期和金额后剩下的中文 | `孙女`、`生日`、`办儿` |
| 已还记号 | `已还`、`✓`、`√`、`还了` | 没有金额时返回 `onlyMark=true` |

切分多次还礼：先按换行、分号、斜杠切分，再按"年份或节令开头"切分；每段独立解析成一个草稿。例如"10年8月1日 生日 500 / 11年正月 50"得到两个草稿。前端逐个提交还礼接口，每次一个草稿。

每个草稿带 `confidence` 字段：日期、金额、事项都解析出来时为 high；缺少任意一项时为 low，前端把缺少的字段标成琥珀色，提醒用户补全。解析失败不报错，返回空草稿，由用户手动填写。

人详情时间线的响应结构：

```json
{
  "groups": [
    {
      "event": { "id": 5, "name": "小明升学宴", "type": "school", "eventDate": "2024-08-16", "host": "other" },
      "inCent": 60000, "outCent": 0,
      "parts": [ { "label": "人情礼", "cent": 50000 }, { "label": "火炮", "cent": 10000 } ],
      "records": [
        { "id": 812, "direction": "in", "itemKind": "cash", "itemKindLabel": "现金",
          "bookId": 2, "bookName": "2024 人情礼簿", "originBookName": "",
          "amountCent": 50000, "giftName": "", "giftValueCent": 0, "totalCent": 50000,
          "occurredOn": "2024-08-16", "datePrecision": "day", "status": "pending", "remark": "",
          "paperNote": "", "paperPage": "1-10", "repayCount": 0 }
      ]
    }
  ]
}
```

- 分组按事项日期倒序；事项没有日期时，用组内最新一条记录的日期代替。
- `parts` 按名目合计生成，前端直接拼成"人情礼 500 + 火炮 100 = 600"这样的文字。
- `originBookName` 只在记录发生过合并（`origin_book_id != book_id`）时才有值。
- 时间线不分页。单个人的记录数量是几十条级别，一次返回更简单。如果之后出现超过 500 条的情况，再改成按事项分页。

```json
{
  "event": { "id": 5, "name": "小明升学宴" },

  "persons": [
    {
      "person": { "id": 12, "name": "张三", "relation": "relative" },
      "inCent": 60000, "outCent": 0, "pendingCount": 2,
      "details": [
        { "bookName": "2024 人情礼簿", "itemKindLabel": "现金", "direction": "in", "cent": 50000, "recordIds": [812] },
        { "bookName": "火炮簿", "itemKindLabel": "火炮", "direction": "in", "cent": 10000, "recordIds": [813] }
      ]
    }
  ]
}
```

前端的"来礼 / 回礼 / 未回"三个标签页都基于 `persons` 在客户端过滤，不再单独请求接口。

### 搜索

搜索分两种：全局搜索和范围内搜索。

#### 全局搜索

`GET /search?q=张&limit=5`，按类别分组返回：

```json
{
  "intent": "text",
  "persons": { "total": 3, "items": [] },
  "events": { "total": 1, "items": [] },
  "books": { "total": 0, "items": [] },
  "records": { "total": 8, "items": [] }
}
```

后端先识别关键词的意图，再决定搜什么：

| 意图 | 关键词示例 | 搜索范围 |
| --- | --- | --- |
| `text` | `张`、`zs`、`孙女`、`被面` | 人：姓名包含、全拼前缀、首字母前缀；事项、本子：名称包含；记录：备注、礼品名、纸本标注包含 |
| `amount` | `500`、`¥500`、`伍佰` | 记录：`total_cent` 等于该金额；大写金额先转换成数字 |
| `amount_range` | `500-1000` | 记录：金额在区间内 |
| `year` | `2011`、`11年` | 事项：日期在该年；记录：日期在该年 |
| `page` | `第1-10页`、`p1-10` | 记录：`paper_page` 等于该页码 |

识别不出意图时按 `text` 处理。纯数字同时可能是金额和年份，比如 `2011`：四位数且在 1950 到当前年份之间时，同时返回金额和年份两类结果。

- 每类最多返回 `limit` 条，`total` 为该类总数，供前端显示"查看全部 23 条"。
- 记录结果按 `occurred_on DESC` 排序，并带上 `matchField`（name、remark、giftName、paperNote、amount），前端据此决定高亮哪个字段。
- 数据量在万级以内，直接用 `LIKE '%q%'`。规模超过这个量级后，再给 `remark`、`gift_name`、`paper_note` 加 MySQL ngram 全文索引。
- `GET /search/records?q=&page=` 返回记录类的完整分页结果，供"查看全部"使用。人、事项、本子的"查看全部"直接跳到对应列表页，并带上 keyword。

#### 范围内搜索

各列表接口都支持 `keyword` 参数，语义与全局搜索相同（包括金额、页码意图），只是限定在当前范围内：

| 接口 | 范围 |
| --- | --- |
| `GET /records?bookId=2&keyword=` | 某个礼簿内 |
| `GET /records?eventId=5&keyword=` | 某个事项内 |
| `GET /views/person-timeline?personId=&keyword=` | 某个亲友的记录内 |
| `GET /persons?keyword=` | 亲友列表 |
| `GET /events?keyword=` | 事项列表 |

意图识别的代码放在 `component/search/service/intent.go`，所有接口共用，保证"搜 500"在任何地方的含义都一样。

## 关键事务

### 合并本子

```text
BEGIN
  SELECT ... FROM book WHERE id IN (sources + target) FOR UPDATE
  校验：target 为 normal；sources 均为 normal，不包含 target，且至少一个
  n := UPDATE record SET book_id = target WHERE owner_id = ? AND book_id IN (sources)
  UPDATE book SET merged_into_id = target WHERE merged_into_id IN (sources)
  UPDATE book SET status='merged', merged_into_id=target, merged_at=NOW(3) WHERE id IN (sources)
  INSERT book_merge_log(source 快照, n, cross_category)
COMMIT
```

合并不改 `origin_book_id` 和 `item_kind`。所以跨类别合并之后，按名目统计和追溯原本子都不受影响，这一点对应 `fen.md` 3.5 节的要求。

### 识别批量写入

```text
BEGIN
  锁定 recognize_task，committed 必须为 0
  对每个勾选项：
    解析人（personId 或 personName，与新建记录规则相同；有歧义的项必须由前端先指定）
    校验（同新建记录，但不做重复检测，只在响应中标记疑似重复）
    INSERT record(source='recognize', recognize_task_id=task.id, paper_page, paper_seq, paper_note)
    对该项每个用户保留的 repayDraft：按还礼接口的事务步骤生成送礼记录与关联（复用同一个 service 方法）
  pageTotal 不为空时：UPSERT paper_page_check
  UPDATE recognize_task SET committed = 1
COMMIT
```

任一项校验失败时，整批回滚，返回 400，`custom.itemErrors` 为 `[{index, field, message}]`，前端据此定位到对应行。全部成功或全部失败，避免出现"写进去一半"的状态。

## 识别链路

### 流程

```text
上传 ─> 校验（jpg/png、≤5MB，按文件头判断类型而不是扩展名）
     ─> 落盘 data/uploads/YYYYMM/<sha256>.<ext>
     ─> 建 task(pending) 并立即返回
     ─> 后台 goroutine：running ─> 调用 Recognizer ─> 解析 ─> 校验 ─> 匹配增强 ─> succeeded/failed
前端每 1.5 秒轮询，最多 60 秒；超时后 task 置为 failed，error_message="识别超时"
```

后台 goroutine 使用独立的、带超时的 ctx，不复用请求 ctx。同时用一个容量为 2 的信号量限制并发，避免短时间连续上传打爆模型配额。服务重启时，把仍处于 pending 或 running 的 task 统一置为 failed，提示用户重试。

### 接口定义

```go
// Recognizer 把一张礼簿照片识别成候选记录，实现方负责调用具体厂商。
type Recognizer interface {
	Recognize(ctx context.Context, img Image) (*Result, error)
	Name() string
}

type Image struct {
	Data []byte
	MIME string
}

type Result struct {
	Model string
	Raw   string
	Items []Item
}

type Item struct {
	Name       string  `json:"name"`
	AmountYuan float64 `json:"amount"`
	GiftName   string  `json:"giftName"`
	ItemKind   string  `json:"itemKind"`
	Direction  string  `json:"direction"`
	Date       string  `json:"date"`
	Raw        string  `json:"raw"`
	Confidence float64 `json:"confidence"`
}
```

默认实现 `openaiCompatRecognizer`：使用 OpenAI 兼容的 `/chat/completions` 接口，把图片转成 `data:<mime>;base64,...` 放进 `image_url`，要求模型只输出 JSON。多数国内外视觉模型都提供这种兼容接口，切换厂商只需要改配置里的 `baseURL` 和 `model`。如果要接入不兼容的厂商，就新增一个实现，并在 `provider` 配置里注册。

### Prompt

典型的纸本页结构：照片常常是横拍的；每位来客占一行（竖排书写时为一列），依次是姓名、"贺礼"字样、大写金额、手写的还礼标注、阿拉伯数字金额；页头有页码，例如"(1-10)"；页脚有本页合计，例如"1070元"。

```text
你是礼簿录入助手。图片是一页中文人情礼簿，可能旋转了 90 度，请先按文字方向理解版面。
每位来客占一行或一列，通常包含：姓名、"贺礼"等字样、大写金额（如"伍拾元""壹佰元"）、
阿拉伯数字金额（如 50）、以及字迹较小的手写还礼标注（如"11年国庆 孙女 100元 火炮20元"）。
页面角落可能有页码（如"(1-10)"）和本页合计（如"1070元"）。
按纸本顺序逐位识别，只输出 JSON，不要任何解释：
{"page":"页码或空","pageTotal":本页合计数字或null,
 "items":[{"seq":序号从1开始,"name":"","amountUpper":"大写原文","amountLower":阿拉伯数字或null,
 "amount":最终判定的元,"giftName":"","itemKind":"cash|huopao|gift","direction":"in",
 "note":"还礼标注原文，没有则空","raw":"整行原文","confidence":0到1}]}
规则：大写金额与阿拉伯数字一致时 amount 取该值；不一致时以大写为准并把 confidence 降到 0.5 以下；
看不清的字保留原样并降低 confidence；标注照抄，不要改写；礼簿默认是收礼。
```

### 解析与增强

1. 用 `utils.UnmarshalLLMJSON` 去掉代码围栏后反序列化。解析失败时把 task 置为 failed，`raw_response` 照常保存。
1. 逐项清洗：姓名去掉空白和标点；金额小于 0 的置为 0；`itemKind`、`direction` 不合法的置空，留给用户选择。
1. 匹配增强：按姓名查人，在每项上补充 `match` 字段：`{"status":"single|none|multiple","personId":12,"candidates":[...]}`。
1. 匹配疑似重复：如果用户在上传时已经选定了事项和本子，就按"人、事项、本子、名目"标出 `duplicateOf`。
1. 大小写核对：`amountUpper` 转成数字后与 `amountLower` 比较，不一致时在该项上加 `amountMismatch=true`。
1. 标注解析：`note` 不为空时，调用纸本标注解析器，把结果放进该项的 `repayDrafts` 数组，每个元素的结构与还礼接口的请求体相同。
1. 本页核对：计算所有项的金额之和，与 `pageTotal` 比较，在 task 上记录 `sumCent` 和 `pageTotalCent`。

## 日志

- 每个请求一行访问日志，包含 `requestId`、`ownerId`、`path`、`status`、`latencyMs`。
- 写操作在 service 层记录一行业务日志，例如 `record.create id=812 person=12`。
- 识别记录 `taskId`、`model`、`latencyMs`、`itemCount`，不记录图片内容和 API Key。
- 金额、姓名属于个人数据，第二阶段上线后只在 debug 级别输出。
